## Andy's decisions (2026-10-22)

- **Owner:** reuse `resolveOwnerIdForCreator` (ADR 0118). The owner is the calling rep's `partners.pipedrive_user_id`, which only Andy and Richard have; anyone else gets its existing default. Never resolve any other owner.
- **Organization:** the project's company is the Pipedrive organization (the partner): `companies.pipedrive_org_id`. The person is `contacts.pipedrive_person_id` from the project. **No name-based upsert anywhere.**
- **Title:** the existing pattern in `deal.ts` (`Arxys Quote - {company} - {project} - {date}`), with the project's company name in the company slot.
- **Pipeline and stage:** pipeline "Partner Projects", stage "New Deal" (confirm the exact spelling in the Phase B dry run). Resolve both by exact name at run time and refuse when either is missing. Do **not** call `resolveStageId` in `lookups.ts`: it caches one stage id regardless of pipeline, so it would hand back the partner path's "Project Pipeline" stage, or poison that cache for the partner path. Add a separate resolver for this pipeline.
- **Deal field:** create `arxys_project_id` once in Phase B, type text, value `projects.id`. The code resolves its key by name at run time and refuses to create a deal when the field does not exist. Do not add it to `CUSTOM_FIELDS`.
- **Money on the deal:** send `currency: "USD"`. Never send `value`: Pipedrive computes it from the attached products (see the value-locked bug family behind ADR 0098).
- **Double click:** two calls for the same calc, or for any calc in the same revision lineage (`parent_submission_id`, ADR 0093), must never create two deals. Take a database claim **before** `POST /api/v2/deals`, keyed on the lineage root. A claim that has no deal id yet means a create may have reached Pipedrive: refuse with "a deal may already exist, check Pipedrive", and never retry the create automatically. The simplest likely shape is a small claim table with a unique key on the lineage root; if something existing already does this safely, use it and record why. A new table is a migration: see the standing rules.
  - **The lineage can split.** `parent_submission_id` is `on delete set null` (ADR 0093), so deleting a middle revision makes its child a new root with a different claim key, and the child could then create a second deal. Guard it two ways: the claim row references the root submission `on delete restrict`, and the claim table also carries `project_id` with a unique key on it, so Step 5 allows one portal-built deal per project (Andy's decision above; record it in the ADR with "revisit when options land"). Cover the deleted-middle-revision case in the PGlite run.
  - **Only the lineage leaf creates the deal.** Refuse when another submission has `parent_submission_id` = this `submissionId` (the calc is superseded), so a deal is never built from an older BOM.
  - **Claim table access:** RLS enabled; internal users may select; inserts and updates go through the service role only. Hand the rest to security-review.
  - **A claim stuck with no deal id** has a recovery path: a small script for Andy (dry run by default, `--apply` plus typed CONFIRM) that either attaches a deal id Andy names after he checks Pipedrive, or releases the claim. Write it in Phase A, run only its dry run against mocks, and record the procedure in the ADR.
- **One portal-built deal per project (2026-10-23):** Andy approved the unique `project_id` key on the claim table for Step 5. It is a deliberate scope cut, recorded in the ADR, to revisit when options and phases land.
- **Pricing check:** Andy expects Pipedrive to fill each line's price from the product. Check the v2 docs for whether `item_price` is required on `POST /api/v2/deals/{id}/products`. Keep sending the product's own price verbatim either way. If the docs say it is optional and defaults to the product price, report that at the Phase A stop as an option for Andy; do not change the design yourself. ## Phase A: library and mocked tests (no live Pipedrive call of any kind)

Everything sits behind `PROJECT_DEAL_PRODUCTS` (default off). Write server-side functions under `src/lib/pipedrive/` or `src/lib/projects/` following existing layout. No screen calls them yet. Each function takes an explicit actor (a `partners.id`) and verifies itself that the actor is an active internal user or admin. A future server action passes the session's user; the Phase B script passes the rep Andy names, after its own check. The actor is what `deal_line_syncs.created_by` records.

1. **Source of the BOM.** Read the BOM only from the banked design row (`submission_system_designs`), looked up by `submissionId`. Never accept a BOM, a price or a SKU list from the caller. Refuse when the calc is not linked in `project_submissions`, or is linked but has no banked design (Step 4 notes N-1 and S-3: only rows linked in `project_submissions` count, and a linked calc with no design row is a failed save).
2. **`previewDealLines(submissionId, actor)`** returns lines `{ sku, qty, role, pipedriveProductId, unitPrice }` plus a `fingerprint`. Use the existing `DealLineFingerprint[]` shape (`src/lib/projects/types.ts`) and compare with `sameLineItems` in `src/lib/projects/line-items.ts`; do not invent a separate hash. Set `line_amount` to `null` in the preview fingerprint: computing qty times price is price math. Build the lines in a fixed order (sku, then role) before fingerprinting, because the shape has no role field and one SKU can appear in two roles. The preview fingerprint is compared only with a fresh preview (item 3). Never compare it with a deal read-back: Pipedrive fills `line_amount` and `name` and leaves `code` null there, so they never match. The deal is checked against the BOM with `diffDealLines`, and the Step 6 gate compares deal read-backs (`fingerprintDealProducts`) with each other. Resolve SKU to product by exact `code` from one full `GET /api/v2/products` read. The USD price comes from the Pipedrive product and is passed through verbatim. **Never** read prices from `current_products` here, and do no price math (no totals, no discounts, no rounding). Refuse the whole preview, listing every offender, when a product is missing, shares its code with another product, has `is_linkable=false`, is $0, or carries the `[MKT]` or `[CFQ]` name prefix (`pdName` in `product-sync.ts`).
3. **`createProjectDeal(submissionId, previewFingerprint, actor)`** is the only deal writer. It re-runs the preview itself and refuses if the fresh fingerprint differs from the one the rep confirmed, so a price changed in Pipedrive after confirmation cannot slip through and the caller never supplies lines or prices. Then:
   - Take the lineage claim (see "Double click" above).
   - Create the deal with `POST /api/v2/deals` using the owner, organization, person, title, pipeline, stage, currency and `arxys_project_id` set out in Andy's decisions. Check how the v2 deal body takes custom fields, and verify against the Pipedrive v2 docs and the existing client, not memory.
   - Record the deal id on the claim, then on the submission the way the portal links a submission to its deal today (`submissions.pipedrive_deal_id`, written by the service role under the ADR 0167 guard), so My Pipeline and `groupIntoDeals` behave as for any deal.
   - Insert one `deal_line_syncs` row per line as `pending` before any POST, then add lines one at a time with `POST /api/v2/deals/{id}/products` (`product_id`, `item_price`, `quantity`, and the line's role in the deal product's comment field, so diff and retry can tell two roles of one SKU apart; check the v2 field name). Mark each `added` with the attachment id the response returns, or `failed` with the error text. The unique key (`pipedrive_deal_id`, `sku`, `role`) is what makes a retry safe.
   - Before returning, read the deal's lines back and run `diffDealLines`. Return its result with the deal id, so every create checks itself.
   - Partial failure leaves the deal in place with a clear "lines pending" state and a non-fatal result for the rep. Never delete the deal automatically.
4. **`retryMissingLines(dealId, actor)`** adds only `pending` and `failed` lines, never an `added` one, and never duplicates. **Always** read the deal's current lines first, on every retry, and mark any row whose line already exists (matching product id and the role in the comment) as `added` instead of posting it. A `pending` row can mean the process died after the POST reached Pipedrive (function timeout, deploy, crash), so a timeout is only one of the ways a line can exist with no `added` row. Two retries running at once must not both post a line: claim each row with a conditional update from `pending`/`failed` to a new `sending` status and post only the rows this call claimed. Holding a lock per deal does not work over PostgREST, so do not try it. The ledger's status check allows only `pending`, `added` and `failed`, so add `sending` to it in the same migration as the claim table (with its rollback). A `sending` row older than a few minutes is treated as retryable, after the same read of the deal's lines.
5. **`diffDealLines(dealId, submissionId)`** compares the banked BOM with the deal's current lines by SKU and role (qty and role differences, extra and missing lines), using a product id to code map from the product read, because the deal cache stores no codes, and the role from each line's comment. Read the lines with the v2 deal products endpoint. Check the exact path in the v2 docs, since the v1 one is out of support. It is read-only and used for revisions in place of rewriting lines.
6. **ADR 0098 retry note.** The "ACTION NEEDED" note is written at `src/lib/pipedrive/deal.ts:442` on the revise path. Step 4 (ADR 0169) makes project calcs skip Pipedrive entirely, so a portal-built deal should never reach it. Confirm that, record it in the ADR, and change nothing. Change only that note text, to point at the diff, if you find a path that does reach it.
7. **Tests with a mocked client.**
   - Preview: every refusal case above, plus a duplicate code on an unrelated SKU that the BOM does not use (must not block); the fingerprint uses the `DealLineFingerprint` shape.
   - Create: fingerprint match and mismatch; an actor who is not internal; a calc not linked to a project; a linked calc with no design row; flag off; `arxys_project_id` field missing; pipeline or stage missing; the partner path's stage cache untouched after a project create; first line fails, middle line fails, last line fails; a 429 mid-run; retry after partial failure adds only the missing lines; retry after a timeout where the line already exists; two retries at once; a double click creating the deal twice, and a second create from a revision of the same lineage (neither creates a second deal); a second create after a middle revision was deleted (refused by the project key); a create from a superseded calc (refused); a claim left with no deal id (refused, no create); retry with a `pending` row whose line already exists in Pipedrive (marked `added`, no POST); a stale `sending` row. The create body sends `currency: "USD"`, no `value`, the owner from `resolveOwnerIdForCreator` (Andy, Richard, and the default for any other internal actor), and the role comment on each line. The read-back diff runs and comes back clean.
   - Diff: equal, missing, extra, quantity mismatch, and one SKU in two roles.
   - No price math: assert the `item_price` sent equals `String(product price)` from the product read, string for string (the ledger's `numeric(12,2)` column is not the comparison).
   - The partner path's Pipedrive payload snapshots from the Step 4 harness still pass unchanged.
   - Run the claim and ledger SQL (concurrent claim, conditional row claim) in PGlite in the scratchpad against the real migrations plus the new one.
