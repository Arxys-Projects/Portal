## What changed

The EPYC 9135 (V700/V800) is EOL and the V400's 9115 was replaced on the same part
consolidation. All three families moved to the **AMD EPYC 9015** — 8C/16T, 3.6 GHz
base, 4.1 GHz turbo, PassMark 30689, 64 MB cache — collapsing V500 through V800 onto
one CPU tier. Camera capacity re-tiered with it: **V400 200 → 150**, **V700/V800
325 → 275** (matching V500/V600, which were untouched).

11 rows: `VX5-V400-128/-160/-192`, `VX5-V400-128-NCD`, `VX5-V400-192-NCD`,
`VX5-V700-384/-480/-576`, `VX5-V800-576/-720/-864`.

### One real behavior change

At a 200-camera ceiling a single V400 absorbed a 150-camera job; at 150 it cannot.
Camera-dense, storage-light deals therefore size up. Measured against live MSRPs:

| Scenario | Before | After | Delta |
|---|---|---|---|
| 150 cams / 100 TB | 1 × VX5-V400-160 $34,206 | 1 × VX5-V500-192 $42,577 | +$8,371 |
| 275 cams / 300 TB | 1 × VX5-V700-384 $66,481 | 2 × VX5-V500-192 $85,154 | +$18,673 |
| 600 cams / 1200 TB | 3 × VX5-V700-480 $227,985 | unchanged | — |
| 900 cams / 1800 TB | 4 × VX5-V700-576 $343,064 | unchanged | — |

Storage-driven deals are unaffected; the change bites only where the camera ceiling
was the binding constraint. This is the recommender behaving correctly under the new
ceiling, not a regression.

### Existing quotes are not retroactively updated

`project_quotes` is an immutable snapshot store, so quotes generated before the
apply keep their old figures by design. 126 of the 184 most recent quotes reference
an affected SKU; exactly one references an `-NCD` SKU (quote
`5746d116-1da6-4451-aec8-2bf3ccd17f72`, Pipedrive deal 5508, generated 2026-09-03),
whose snapshot still reads `AMD EPYC 9005 3.3Ghz 16/32 Core` / 200 cams.

Confirmed read-only that a **fresh** generation resolves the new values for that
deal, including the hidden NCD SKU — `assemble.ts` queries `product_specs` by exact
id with no catalog-visibility filter, so both `VX5-V400-128` and
`VX5-V400-128-NCD` now return `AMD EPYC 9015 3.6Ghz 8/16 Core` / `8C/16T` / 30689 /
`150/150`. **No fresh quote was generated** — that writes a new `project_quotes`
version and is left to a human.

## Rollback

`supabase/rollback/v400-v700-v800-9015-cpu-refresh-rollback.sql` restores the
pre-change values captured live immediately before the apply. It needs four
statements rather than three: `VX5-V400-128` had already been hand-edited to most
of the 9015 numbers through the admin form earlier the same day
(`product_specs_audit` #97), so it is restored separately — folding it in with its
siblings would discard that edit. V700 and V800 share a `cpu_model_full` string but
not a turbo figure (4.25 vs 4.55 Ghz) and cannot be collapsed either.

Running the rollback appends further `product_specs_audit` rows, also with
`updated_by = null`. It does **not** revert the test-fixture changes in the paired
commit — revert those alongside it, or the suite will fail against restored data.

## Still open

`max_bandwidth_mbps` was deliberately left alone. The same 2026-09-14 admin edit
that pre-changed `VX5-V400-128` also dropped its `max_bandwidth_mbps` from 2000 to
1600, which is outside this migration's column set. `VX5-V400-128` therefore sits at
1600 while the other four V400 rows sit at 2000 — an intra-family inconsistency this
migration neither created nor resolved. Decide separately.

### What the first migration got wrong, and the tell

The error was visible in the data it produced: it left V700/V800 on an 8C/16T CPU
while keeping them at 275 cameras, when that same 8C/16T part caps the V400 at 150.
Same silicon, near-double the ceiling, is not a coherent spec — and a spec that
contradicts itself is worth more than a clean `SELECT` that merely confirms the
write landed. Verification that only asks "did the values I intended get written"
cannot catch a wrong intent; the cross-check that would have caught this is
"does the resulting tier structure make sense".

### Open label question

The V400 label names the **part** (`9015`) while the V500–V800 label names the
**series** (`9005`, for what is a 9115). Copied verbatim from the live V500 rows at
the product owner's direction; flagged here because the two conventions disagree
and a future reader will notice. Changing it would touch all 13 rows.
